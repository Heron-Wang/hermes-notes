# JavaScript 位运算返回有符号整数，导致哈希值对不上

> **日期**: 2026-08-12  
> **分类**: 踩坑记录  
> **标签**: JavaScript, 前端, 哈希  
> **来源**: hermes

---

## 背景/问题

在给静态网站做前端密码保护时，用了 djb2 哈希算法把密码转成数字存储。但写完代码一测试，发现输入正确密码后哈希值怎么都对不上——明明算法没问题，哈希结果却差了十万八千里。

## 原因分析

JavaScript 的位运算（`<<`、`>>`、`&`、`|`）有一个很多人不知道的特性：**返回值是 32 位有符号整数**，范围是 -2,147,483,648 到 2,147,483,647。

djb2 哈希在计算过程中，数字会不断累加变大，超过 32 位范围后通过 `& 0xffffffff` 截断。但问题是：

```javascript
// 看起来是在做无符号截断
h = h & 0xffffffff;
// 实际上 JS 返回的是有符号数！
// 如果结果的最高位是 1，JS 会把它解释成负数
```

比如密码哈希后的正确值应该是 `3437355211`（无符号），但 JS 返回的是 `-857612085`（有符号）。两个数字在二进制层面是一样的，但 JS 比较时认为它们不相等。

## 解决方案

用**零填充右移** `>>>0` 把有符号整数转成无符号整数：

```javascript
// ❌ 错误写法 — 返回有符号数，可能为负数
function djb2Hash(str) {
  let h = 5381;
  for (let i = 0; i < str.length; i++) {
    h = ((h << 5) + h) + str.charCodeAt(i);
    h = h & 0xffffffff;
  }
  return h;  // 可能返回 -857612085
}

// ✅ 正确写法 — >>>0 转为无符号
function djb2Hash(str) {
  let h = 5381;
  for (let i = 0; i < str.length; i++) {
    h = ((h << 5) + h) + str.charCodeAt(i);
    h = h & 0xffffffff;
  }
  return h >>> 0;  // 返回 3437355211
}
```

`>>>` 是无符号右移运算符，`>>>0` 表示右移 0 位——不移位，但会把结果转成无符号 32 位整数。

## 避坑提示

- **凡是 JS 里用了位运算的哈希函数**，最后 return 一定要加 `>>>0`
- 用 Node.js 验证哈希值时，`console.log()` 打印有符号数，容易误以为算错了
- 如果哈希值要在前端和后端之间传递，确保两端都用无符号整数比较
- djb2 不是加密级哈希，只适合前端防肉眼看到明文，不能用于真正的安全场景
