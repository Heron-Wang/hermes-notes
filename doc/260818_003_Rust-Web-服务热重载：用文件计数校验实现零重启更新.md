# Rust Web 服务热重载：用文件计数校验实现零重启更新

> **日期**: 2026-08-18  
> **分类**: 架构设计  
> **标签**: Rust, 热重载, heron-web, Mutex, 文件监听, 性能优化  
> **来源**: hermes

---

## 背景/问题

heron-web 是一个用 Rust 写的个人网站后端（笔记管理 + 留言板 + 作品集），笔记以 Markdown 文件存在 `hermes-notes/doc/` 目录。最初的实现是每次请求都重新扫描整个 doc 目录来加载笔记列表——当笔记数量增长到 45+ 篇时，每次 API 请求都做一次 `fs::read_dir` + 解析所有 .md 文件，性能不理想。

更痛点的是：每次新增/删除笔记文件后需要手动重启 heron-web 服务才能生效。想要实现**热重载**（修改文件后不重启服务即生效），但又不想引入文件系统监听库（如 `notify`）增加依赖。

## 解决方案

### 设计思路：文件计数校验

用"目录中 .md 文件数量"作为变更检测信号——每次 API 请求前检查文件数是否变化，变了就重新加载，没变就用缓存。

### 核心数据结构

```rust
// store.rs
use std::sync::Mutex;

pub struct AppState {
    pub notes: Mutex<Vec<Note>>,           // 缓存的笔记列表
    pub notes_file_count: Mutex<usize>,     // 上次加载时的文件数
}
```

### check_reload_notes 方法

```rust
// service.rs
pub fn check_reload_notes(&self) {
    let current_count = match fs::read_dir(&self.notes_dir) {
        Ok(entries) => entries
            .filter_map(|e| e.ok())
            .filter(|e| e.path().extension().map_or(false, |ext| ext == "md"))
            .count(),
        Err(_) => return,
    };

    let mut cached_count = self.notes_file_count.lock().unwrap();
    if *cached_count != current_count {
        // 文件数变了，重新加载
        if let Ok(notes) = self.load_notes() {
            *self.notes.lock().unwrap() = notes;
            *cached_count = current_count;
        }
    }
    // 否则用缓存，零开销
}
```

### 在路由中调用

在每个涉及笔记的 API 路由入口调用 `check_reload_notes()`：

```rust
// routes.rs
async fn list_notes(state: web::Data<Arc<AppState>>) -> impl Responder {
    state.service.check_reload_notes();  // 热重载检查
    let notes = state.notes.lock().unwrap();
    HttpResponse::Ok().json(/* ... */)
}
```

## 性能分析

| 操作 | 每次请求开销 | 备注 |
|------|------------|------|
| **修复前**（全量扫描） | 45 次 `read_dir` + 45 次文件解析 | O(n)，n=笔记数 |
| **修复后**（计数校验） | 1 次 `read_dir` + 1 次计数 | O(1)，与笔记数无关 |
| **触发重载**（文件数变了） | 1 次 `read_dir` + n 次解析 | 仅在文件变更时 |

日常请求（没有文件变更）的开销从 O(n) 降到 O(1)——只需一次 `read_dir` 遍历计数，不解析任何文件内容。

## 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **文件计数校验** | 每次请求比较文件数 | 零依赖、实现简单 | 同数量替换（删一个加一个）检测不到 |
| **notify 库** | inotify/inotify 系统调用 | 实时、精确 | 增加依赖、需要 async 集成 |
| **mtime 校验** | 比较目录修改时间 | 简单 | 目录 mtime 不一定可靠 |
| **定期全量重载** | 定时器周期性重载 | 简单 | 有延迟、浪费 CPU |
| **手动信号** | SIGHUP 触发重载 | 精确控制 | 需手动操作 |

文件计数校验的已知局限：如果同时删除一个文件并新增一个文件（数量不变），检测不到变更。对于个人笔记场景（通常是单次新增或删除），这个局限可以接受。

## 避坑提示

- **`set -e` 在验证脚本中会导致 grep 无匹配时退出**：grep 返回 1（无匹配）会被 `set -e` 当作错误，导致脚本提前退出。用 `grep ... || true` 或去掉 `set -e`
- **Mutex 锁顺序很重要**：先锁 `notes_file_count`，再锁 `notes`。如果反过来，在并发请求中可能死锁
- **`fs::read_dir` 的 entries 需要 filter_map**：`read_dir` 返回 `Result<DirEntry>`，部分 entry 可能读取失败（权限等），需要 `filter_map(|e| e.ok())` 跳过
- **文件计数 ≠ 笔记数量**：计数的是 .md 文件数，不是解析后的笔记数。一个 .md 文件可能解析失败（格式错误），但不影响计数校验的变更检测功能

## 相关知识

### Rust 中的 Mutex 使用模式

```rust
// 正确：短作用域锁
{
    let data = state.data.lock().unwrap();
    // 使用 data
} // 锁自动释放

// 错误：长作用域锁（阻塞其他线程）
let data = state.data.lock().unwrap();
// ... 大量操作 ...
// 锁持有时间过长
```

在 Web 服务中，锁的持有时间应该尽可能短——获取锁、读写数据、释放锁。避免在持有锁的情况下做 I/O 操作。

### 代码分层约束

遵循 route → service → store 分层：

```
routes.rs   → HTTP 路由处理，调用 service
service.rs  → 业务逻辑，调用 store
store.rs    → 数据存储，管理 Mutex
```

每层不跨层调用。`check_reload_notes()` 在 service 层定义，在 routes 层调用，操作 store 层的 Mutex。
