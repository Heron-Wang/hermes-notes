## 背景/问题

你做了一个视频自动生成系统（news-video），流程是这样的：用户在网页上点击"生成视频"按钮 → 后端启动一个 7 阶段的流水线（采集新闻 → LLM 处理 → 生成幻灯片 → 截图渲染 → TTS 配音 → ffmpeg 合成 → 发布归档）→ 前端轮询显示进度。

每段视频生成要 3-5 分钟，期间用户可能想中途取消——比如选错了主题、或者发现新闻内容不满意。你在前端加了一个红色"终止任务"按钮，点击后调用 `POST /api/cancel`，后端设置一个取消标志。

但测试时发现：**点了取消按钮，后端返回"取消请求已发送"，但流水线根本没停！** 进度条继续走，ffmpeg 继续合成，直到视频完全生成才结束。取消按钮形同虚设。

这个问题涉及到 Python 多线程编程中的**协作式取消**（cooperative cancellation）模式——不是简单设个标志就完事，你需要在每个关键节点都检查这个标志。

## 原因分析

### 什么是协作式取消？

在 Python 中，线程不能被外部强制终止（没有 `Thread.kill()` 方法）。取消一个正在运行的线程，只能用**协作式取消**：主线程设置一个标志变量，工作线程在合适的时机主动检查这个标志，如果发现被设置了，就主动退出。

这就像两个人配合搬东西：喊"停"的人（主线程）只是举了块"停"的牌子，搬东西的人（工作线程）必须自己抬头看牌子，看到"停"才放下东西。如果搬东西的人一直低着头搬，牌子举再高也没用。

### 取消标志的设计

代码中用了一个模块级字典作为取消标志：

```python
# pipeline.py 第71行
_CANCEL_FLAG = {"cancel": False}

def request_cancel():
    """主线程调用：设置取消标志"""
    _CANCEL_FLAG["cancel"] = True

def is_cancelled() -> bool:
    """工作线程调用：检查是否被取消"""
    return _CANCEL_FLAG["cancel"]
```

为什么用字典而不是简单的布尔变量？因为布尔变量在 Python 中是不可变类型，赋值 `_CANCEL_FLAG = True` 会创建一个新对象，而不是修改原对象。字典是可变类型，`_CANCEL_FLAG["cancel"] = True` 修改的是字典内容，所有引用这个字典的代码都能看到变化。

### 为什么取消没生效？

关键问题在于：`is_cancelled()` 只在流水线的**第①阶段（采集新闻）开始前**检查了一次：

```python
# 原来的代码（有问题）
def run_pipeline(category, count):
    _CANCEL_FLAG["cancel"] = False  # 重置取消标志
    
    # ① 采集新闻
    if is_cancelled():  # ← 只在这里检查了一次！
        log("❌ 任务已取消")
        return None
    
    # ② LLM 处理 — 没有检查 is_cancelled()
    # ③ 生成幻灯片 — 没有检查
    # ④ 截图渲染 — 没有检查
    # ⑤ TTS 配音 — 没有检查
    # ⑥ ffmpeg 合成 — 没有检查
    # ⑦ 发布归档 — 没有检查
```

如果用户在第②阶段之后点击取消，`_CANCEL_FLAG["cancel"]` 确实被设为 `True`，但工作线程已经过了第①阶段的检查点，后面的阶段根本不检查这个标志，所以流水线继续运行到结束。

这就像你在大楼里喊"起火了，快跑"，但只有一楼的人听到了，二楼以上的人继续工作——因为每个楼层没有独立的警报检查。

### 线程安全性分析

`run_pipeline` 在子线程中运行，`request_cancel` 在主线程（Web 请求处理）中调用。它们共享同一个 `_CANCEL_FLAG` 字典。这安全吗？

在 Python 中，由于 **GIL（全局解释器锁）** 的存在，同一时刻只有一个线程能执行 Python 字节码。字典的 `__setitem__` 和 `__getitem__` 操作在 CPython 实现中是原子的（因为它们在 C 层面完成，中间不会释放 GIL）。所以 `_CANCEL_FLAG["cancel"] = True` 和 `_CANCEL_FLAG["cancel"]` 的读取是线程安全的。

但要注意：如果你的标志更复杂（比如嵌套字典 `_CANCEL_FLAG["user"]["cancel"] = True`），两次字典访问之间可能释放 GIL，就不一定安全了。对于简单的单层字典值，GIL 保证了安全性。

## 解决方案

### 步骤 1：在每个阶段添加取消检查点

在每个阶段开始处添加 `is_cancelled()` 检查。取消时设置状态为"已取消"并退出：

```python
# pipeline.py — 在每个阶段开始处添加取消检查

def run_pipeline(category, count):
    _CANCEL_FLAG["cancel"] = False  # 重置取消标志
    
    # ① 采集新闻
    if is_cancelled():
        log("❌ 任务已取消")
        _write_status({**_read_status(), "status": "cancelled",
                       "step": "已取消",
                       "finished_at": datetime.now().isoformat()})
        return None
    
    # ② LLM 处理
    if is_cancelled():   # ← 新增检查点
        log("❌ 任务已取消")
        _write_status({**_read_status(), "status": "cancelled",
                       "step": "已取消",
                       "finished_at": datetime.now().isoformat()})
        return None
    
    # ③ 生成幻灯片
    if is_cancelled():   # ← 新增检查点
        # ... 同上
    
    # ④ 截图渲染
    if is_cancelled():   # ← 新增检查点
        # ... 同上
    
    # ⑤ TTS 配音
    if is_cancelled():   # ← 新增检查点
        # ... 同上
    
    # ⑥ ffmpeg 合成
    if is_cancelled():   # ← 新增检查点
        # ... 同上
    
    # ⑦ 发布归档
    if is_cancelled():   # ← 新增检查点
        # ... 同上
```

为了减少重复代码，可以把取消检查封装成装饰器或辅助函数：

```python
def _check_cancel_or_exit():
    """检查取消标志，如果已取消则写状态并返回 True"""
    if is_cancelled():
        log("❌ 任务已取消")
        _write_status({**_read_status(), "status": "cancelled",
                       "step": "已取消",
                       "finished_at": datetime.now().isoformat()})
        return True
    return False

# 使用时更简洁：
if _check_cancel_or_exit():
    return None
```

```bash
# 修复前: 2（1个定义 + 1个检查点）

```

### 步骤 3：处理 ffmpeg 子进程

即使 pipeline 检测到取消并退出，ffmpeg 子进程可能还在运行（特别是合成大视频时）。需要在取消时主动杀掉 ffmpeg：

```python
import signal, subprocess

# 全局变量记录当前 ffmpeg 进程
_ffmpeg_proc = None

def request_cancel():
    """取消时同时杀掉 ffmpeg"""
    _CANCEL_FLAG["cancel"] = True
    if _ffmpeg_proc and _ffmpeg_proc.poll() is None:
        _ffmpeg_proc.send_signal(signal.SIGTERM)  # 先发 SIGTERM
        try:
            _ffmpeg_proc.wait(timeout=5)  # 等5秒优雅退出
        except subprocess.TimeoutExpired:
            _ffmpeg_proc.kill()  # 强制杀
        log("ffmpeg 进程已终止")
```

## 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **协作式取消（本文方案）** | 工作线程在每个检查点主动检查标志 | 简单、线程安全、可控 | 只能在阶段边界取消，不能在阶段中间取消 | 阶段明确的流水线 |
| 强制终止线程 | 用 `ctypes` 调用 `PyThreadState_SetAsyncExc` | 可以在任何时刻终止 | 不安全，可能导致资源泄漏、数据损坏 | 不推荐，最后手段 |
| 进程级取消 | 每个任务用独立进程，取消时杀进程 | 干净彻底，无资源泄漏 | 进程启动开销大，状态共享复杂 | 隔离性要求高的场景 |
| asyncio 取消 | 用 `asyncio.Task.cancel()` + `CancelledError` | 语言原生支持，优雅 | 需要整个代码库是 async | 新项目、I/O 密集型 |
| 信号 + 超时 | 给子进程设 SIGALRM 超时 | 可以限制单阶段时间 | 信号处理复杂，跨平台问题 | 需要硬超时的场景 |

## 避坑提示

- **取消不是即时生效的**。协作式取消只能在下一次检查点生效。如果某个阶段耗时长（比如 ffmpeg 合成 2 分钟），用户点击取消后要等这个阶段结束才能停。解决方案：在长阶段内部也插入检查点，或者直接杀子进程。
- **不要用布尔变量做跨线程标志**。`_CANCEL_FLAG = False` 在赋值时会创建新对象，其他线程引用的还是旧对象。用字典（`{"cancel": False}`）或 `threading.Event` 代替。
- **`threading.Event` 是更好的选择**。`Event.set()` / `Event.is_set()` 语义更清晰，且专为线程间通信设计：
  ```python
  cancel_event = threading.Event()
  # 设置取消: cancel_event.set()
  # 检查取消: if cancel_event.is_set()
  ```
- **取消后要清理子进程**。pipeline 退出了，但 ffmpeg/subprocess 可能还在后台跑。取消逻辑中要主动杀掉子进程，否则 CPU 和内存会被白白占用。
- **状态写入要原子化**。取消时写 `pipeline_status.json` 要用"写临时文件 + 重命名"的方式，避免并发写入导致文件损坏。
- **重置标志要在任务开始前**。`_CANCEL_FLAG["cancel"] = False` 必须在 `run_pipeline` 开头执行，否则上次任务的取消标志会影响下次任务。

## 相关知识

### Python GIL 与线程安全

Python 的 GIL（Global Interpreter Lock）是一个全局互斥锁，保证同一时刻只有一个线程执行 Python 字节码。这意味着：

- **简单的字典/列表操作是线程安全的**——因为 `dict.__setitem__` 在 C 层面是原子的，不会在中间释放 GIL
- **但复合操作不是**——`if key in d: d[key] = value` 两次字典访问之间可能发生线程切换
- **`threading.Event` 内部用了锁**，所以 `set()` 和 `is_set()` 是完全线程安全的

### asyncio 的取消机制

如果你的项目是异步的（async/await），Python 提供了更优雅的取消机制：

```python
task = asyncio.create_task(run_pipeline())
# 取消时：
task.cancel()
# run_pipeline 中捕获 CancelledError：
try:
    await long_running_operation()
except asyncio.CancelledError:
    # 清理资源
    raise  # 重新抛出，让上层处理
```

asyncio 的取消会在下一个 `await` 点抛出 `CancelledError`，不需要你手动添加检查点。但前提是整个调用链都是 async 的。

### ffmpeg 进程管理

ffmpeg 是外部子进程，Python 的 `subprocess.Popen` 提供了几种终止方式：

| 信号 | 行为 | 命令 |
|------|------|------|
| `SIGTERM` | 优雅终止，ffmpeg 会写完当前帧 | `proc.send_signal(signal.SIGTERM)` |
| `SIGKILL` | 强制杀死，不可拦截 | `proc.kill()` |
| `SIGINT` | 相当于 Ctrl+C | `proc.send_signal(signal.SIGINT)` |

推荐先发 `SIGTERM` 等 5 秒，超时再 `SIGKILL`。因为 `SIGTERM` 让 ffmpeg 有机会清理临时文件和写完最后一帧。
