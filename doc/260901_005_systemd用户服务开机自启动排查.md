# systemd 用户服务开机自启动排查：linger、network-online.target 与挂载依赖

## 背景

NAS 重启后，`hermes-gateway.service` 虽然状态为 `enabled` 且 linger 已启用，但服务未自动启动（`inactive (dead)`）。需要手动 `systemctl --user start hermes-gateway` 才恢复。

## 排查过程

### 1. 确认服务状态

```bash
systemctl --user status hermes-gateway
# ○ hermes-gateway.service ... Active: inactive (dead)
# Loaded: loaded (enabled; preset: enabled)

systemctl --user is-enabled hermes-gateway
# enabled
```

### 2. 检查 linger（用户会话持久化）

```bash
loginctl show-user heron | grep -E "Linger|State"
# State=active
# Linger=yes
```

linger 已启用，理论上 systemd 用户实例应在开机时启动。

### 3. 检查启动列表

```bash
systemctl --user list-dependencies hermes-gateway.service | head -20
# hermes-gateway.service
#   ├─app.slice
#   ├─basic.target
#   │   ├─paths.target
#   │   ├─sockets.target
#   │   └─timers.target
#   ○ └─network-online.target    ← INACTIVE!
```

关键发现：`network-online.target` 是 `○`（inactive），但服务配置了 `Wants=network-online.target`。

### 4. 检查服务依赖配置

```bash
systemctl --user show hermes-gateway --property=After,Requires,Wants,RequiresMountsFor
# Requires=basic.target app.slice
# Wants=network-online.target
# After=app.slice home.mount network-online.target basic.target -.mount
# RequiresMountsFor=/home/heron/.hermes
```

服务依赖链：
- `After=home.mount` — 等待 /home 挂载
- `After=network-online.target` — 等待网络就绪
- `RequiresMountsFor=/home/heron/.hermes` — 需要 .hermes 目录可用

### 5. 检查挂载状态

```bash
# /home 在 sda（机械盘）
systemctl --user show home.mount --property=What,Where,Type
# Where=/home
# What=/dev/mapper/ug_5666F6_1748966670_pool1-volume1
# Type=ext4

# /volume2 在 NVMe
systemctl list-units --type=mount | grep volume
# volume1.mount  loaded active mounted /volume1
# volume2.mount  loaded active mounted /volume2

# state.db 通过符号链接指向 NVMe
ls -la ~/.hermes/state.db
# lrwxrwxrwx ... state.db -> /volume2/hermes-data/state.db
```

### 6. 检查启动日志

```bash
# 查看 boot 列表
journalctl --user -u hermes-gateway --list-boots
# -9 ... Sun 2026-08-23 ... Mon 2026-08-24  (正常运行期)
# -8 ... Mon 2026-08-24 08:00:39 ... 08:00:44  (仅 5 秒)
# -1 ... Mon 2026-08-31 08:00:39 ... 08:00:50  (仅 11 秒)
#  0 ... Tue 2026-09-01 08:00:40 ... 08:00:50  (仅 10 秒)

# 当前 boot 的日志
journalctl --user -u hermes-gateway -b 0 --no-pager --output=cat
# (空 — MaxLevelStore=err 导致 INFO 日志不存储)
```

每次 boot 中 gateway 服务只有几秒的日志记录，之后就没有了。

## 根因分析

综合分析，服务未自启动的可能原因：

1. **`network-online.target` 在用户实例中可能不工作**：`network-online.target` 是系统级 target，用户实例中可能无法正确等待网络就绪
2. **挂载依赖未解析符号链接**：`RequiresMountsFor=/home/heron/.hermes` 检查的是路径 `/home/heron/.hermes`，但 state.db 是符号链接到 `/volume2/hermes-data/`，systemd 可能未跟随符号链接检查 `/volume2` 的挂载状态
3. **用户会话启动时机**：虽然 linger=yes，但用户 systemd 实例的启动可能晚于某些挂载点

## 解决方案

### 方案一：添加开机自启动检查 cron（推荐）

```bash
# 创建一个 cron job，开机后延迟检查 gateway 状态
# crontab -e
@reboot sleep 60 && systemctl --user start hermes-gateway 2>/dev/null
```

### 方案二：修改服务依赖

```bash
# 如果问题是 network-online.target 在用户实例不工作
# 可以添加 RequiresMountsFor=/volume2 确保 NVMe 先挂载
systemctl --user edit hermes-gateway
```

在 override 文件中添加：
```ini
[Service]
RequiresMountsFor=/home/heron/.hermes /volume2
```

### 方案三：使用 systemd timer 替代

```ini
# ~/.config/systemd/user/hermes-gateway-check.timer
[Unit]
Description=Check hermes-gateway at boot

[Timer]
OnBootSec=30
Unit=hermes-gateway-check.service

[Install]
WantedBy=timers.target
```

## 经验总结

| 检查项 | 命令 |
|--------|------|
| 服务是否 enabled | `systemctl --user is-enabled hermes-gateway` |
| 服务是否 running | `systemctl --user status hermes-gateway` |
| linger 是否启用 | `loginctl show-user $USER \| grep Linger` |
| 启动依赖链 | `systemctl --user list-dependencies hermes-gateway` |
| 服务属性 | `systemctl --user show hermes-gateway --property=After,Wants,Requires` |
| 启动历史 | `journalctl --user -u hermes-gateway --list-boots` |

## 坑点

1. **`enabled` + `linger=yes` ≠ 一定会自启动**：systemd 用户服务在 boot 时的启动行为受多种因素影响
2. **`network-online.target` 在用户实例中可能是 inactive**：这不阻止服务启动（只是 `Wants` 不是 `Requires`），但可能影响依赖网络的服务
3. **`RequiresMountsFor` 不跟随符号链接**：`~/.hermes/state.db` → `/volume2/hermes-data/state.db`，但 systemd 只检查 `/home/heron/.hermes` 路径的挂载状态
4. **boot 日志只有几秒**：每次 boot 中用户 journal 只有几秒的记录（08:00:39-08:00:50），之后可能整个用户实例就停止了
5. **用户 journal 可能为空**：`MaxLevelStore=err` 配置导致非 ERROR 日志不存储
