# 小爱音箱 Bridge 性能优化：为什么简单对话要等 127 秒？

> **日期**: 2026-08-13  
> **分类**: 性能优化  
> **标签**: Python, 小爱音箱, 性能优化, Hermes, TTS  
> **来源**: hermes

---

## 背景/问题

家里的小爱音箱通过自建的 Bridge 服务对接了 Hermes Agent（运行在 NAS 上），实现了智能家居语音控制。但上线后发现一个严重影响体验的问题：**简单对话要等 29 秒才能回复，复杂查询直接超时 127 秒**。

想象一下：你对着音箱说"帮我看看几点了"，然后站在那里等了将近半分钟才听到回答。而小爱原生回答只需要 1-2 秒。这种延迟让语音交互变得几乎不可用——用户会本能地以为音箱没听到，重复提问，结果多个请求堆积导致更慢。

问题的核心在于 Bridge 的架构设计：所有请求都走同一条路径（先调 Hermes Agent，再生成 TTS 语音），没有区分简单聊天和需要工具调用的复杂任务。这导致即使问"讲个笑话"这种纯聊天问题，也要等 Hermes 完整启动、加载技能、调用 LLM，白白浪费十几秒。

## 原因分析

通过在 Bridge 代码中添加分阶段计时日志，对三次典型对话进行了耗时拆解：

| 对话内容 | LLM 耗时 | TTS 耗时 | 总耗时 | 走的路径 |
|---------|---------|---------|--------|----------|
| "帮我看看几点了" | 16秒 | 12秒 | 29秒 | Hermes Agent |
| "讲个笑话" | 13秒 | 30秒 | 43秒 | CANNBOT |
| "查询LOS状态" | 120秒超时 | 7秒 | 127秒 | Hermes 超时 |

分析发现**三大性能瓶颈**：

### 瓶颈 1：Hermes Agent 冷启动太慢（16-120 秒）

Hermes 是一个完整的 AI Agent 框架，每次调用 `hermes chat -q "问题"` 时，它要：

1. **加载配置文件** — 读取 `~/.hermes/config.yaml`，初始化 provider
2. **加载技能库** — 扫描 `~/.hermes/skills/` 目录，解析所有 SKILL.md
3. **加载持久记忆** — 从 SQLite 读取 memory 和 user profile
4. **建立 LLM 连接** — 与远端 API 建立 HTTPS 连接
5. **执行推理** — 发送 prompt，等待 LLM 响应

实测冷启动最少 11 秒，如果 Agent 尝试调用工具（如搜索文件、执行命令）但没有找到结果，时间会进一步膨胀到 120 秒超时。

而 CANNBOT（直接调 LLM API）只需要 3.5 秒——因为它不加载技能、不初始化工具、不走 Agent 循环，就是一个简单的 HTTP API 调用。

### 瓶颈 2：Edge TTS 生成慢（12-30 秒）

Bridge 最初配置了 `tts: edge`（微软 Edge TTS），音质好但生成速度慢：

- 短回答（50 字以内）：12 秒
- 长回答（200 字左右）：30 秒

原因是 Edge TTS 需要将文本发送到微软云端服务器合成语音，再下载音频文件。内容越长，合成时间越长。而小爱原生 TTS（`mi`）在本地或小米云端合成，速度快得多。

### 瓶颈 3：单线程同步阻塞

Bridge v1 使用 Python 标准库的 `HTTPServer`：

```python
# v1: 单线程 — 一个请求处理完才能处理下一个
from http.server import HTTPServer, BaseHTTPRequestHandler

server = HTTPServer(("127.0.0.1", 8090), BridgeHandler)
server.serve_forever()
```

`HTTPServer` 是**单线程同步**的——同一时间只能处理一个请求。如果用户连续问了两个问题，第二个请求必须等第一个完全处理完（包括 LLM + TTS）才能开始。虽然 xiaogpt 的请求是串行的（用户说一句等一句），但单线程意味着健康检查（`/health`）也会被阻塞，不便于监控。

更关键的是，即使配置了 `stream: true`（流式响应），由于 HTTPServer 的同步特性，Bridge 必须等 LLM **完整返回**后才开始 TTS 播报——无法做到边生成边播报。

## 排查过程

### 第一步：添加分阶段计时日志

在 Bridge 的 `_process_query` 函数中添加时间戳：

```python
def _process_query(messages, stream=False):
    user_msg = extract_last_user_message(messages)
    t0 = time.time()
    
    if should_use_hermes(user_msg):
        _log(f"→ Hermes (slow): {user_msg[:40]}")
        content = _hermes_chat(user_msg)
        _log(f"← Hermes done in {time.time()-t0:.1f}s")
    else:
        content = _cannbot_chat(messages)
        _log(f"← CANNBOT done in {time.time()-t0:.1f}s")
    
    return content, model_name
```

通过 `journalctl -u xiaomi-bridge -f` 实时观察日志，发现三次对话的耗时分布如上表所示。

### 第二步：隔离 LLM 和 TTS 耗时

为了确认瓶颈在 LLM 还是 TTS，分别在 `_cannbot_chat` 和 `_hermes_chat` 内部也加了计时：

```python
# 在 _cannbot_chat 内部
t_llm = time.time()
body = json.loads(urllib.request.urlopen(req, timeout=30).read())
_log(f"  LLM: {time.time()-t_llm:.1f}s")
```

结果发现：
- CANNBOT LLM 调用：3.5 秒
- Hermes CLI 执行：11-16 秒（冷启动）
- Edge TTS：12-30 秒（与文本长度正相关）

### 第三步：确认 Hermes 冷启动开销

单独测试 Hermes CLI 的启动时间：

```bash
# 测试冷启动（首次调用）
time hermes chat -q "你好" -Q --no-restore-cwd --max-turns 1
# 实测：11.2s

# 测试热启动（紧接着第二次调用）
time hermes chat -q "再见" -Q --no-restore-cwd --max-turns 1
# 实测：8.7s（仍很慢，因为每次都是新进程）
```

结论：Hermes 每次调用都是新进程，没有热启动优势。11 秒的冷启动开销对于语音交互来说不可接受。

### 第四步：分析触发词匹配逻辑

检查 v1 的触发词配置：

```python
# v1: 触发词太宽泛
HERMES_TRIGGER_KEYWORDS = "帮,查,执行,运行,检查,搜索,写,改,创建,删除,部署,看看,查看"
```

问题在于 `帮`、`查`、`看看` 这些词太常见了——"帮我讲个笑话"、"查一下天气"、"看看新闻"都会触发 Hermes 慢路径。而这些问题 CANNBOT 完全能处理。

## 解决方案

基于排查结果，实施了 4 项优化：

### 步骤 1：收窄 Hermes 触发词（最关键）

把宽泛的日常用语去掉，只保留**明确需要工具操作**的动作词：

```python
# v1（优化前）— 太宽泛，几乎所有对话都走 Hermes
HERMES_TRIGGER_KEYWORDS = "帮,查,执行,运行,检查,搜索,写,改,创建,删除,部署,看看,查看"
HERMES_TIMEOUT = 120

# v2（优化后）— 只在真正需要工具时触发
HERMES_TRIGGER_KEYWORDS = "执行,运行,部署,检查系统,搜索,创建文件,删除,重启,启动服务,停止服务,查看服务,查看进程,查看磁盘,查看端口"
HERMES_TIMEOUT = 60
```

关键改动：
- 去掉 `帮`、`查`、`看看`、`查看` 等宽泛词（这些 CANNBOT 能处理）
- 保留 `执行/运行/部署/重启` 等明确的系统操作词
- 超时从 120 秒缩短到 60 秒（超时就降级返回提示，不让用户干等）

效果：90% 的日常对话走 CANNBOT 快路径（3.5 秒），只有 10% 的系统操作走 Hermes。

### 步骤 2：HTTPServer 升级为 ThreadingHTTPServer

```python
# v1: 单线程，一个请求阻塞所有后续请求
from http.server import HTTPServer, BaseHTTPRequestHandler
server = HTTPServer(("127.0.0.1", 8090), BridgeHandler)

# v2: 多线程，每个请求独立处理
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
server = ThreadingHTTPServer(("127.0.0.1", 8090), BridgeHandler)
server.daemon_threads = True  # 主进程退出时自动清理子线程
```

`ThreadingHTTPServer` 为每个请求创建一个新线程，这样：
- 健康检查不会被长请求阻塞
- 多个请求可以并行处理（虽然 xiaogpt 是串行的，但运维更方便）
- `daemon_threads = True` 确保线程随主进程退出，不会僵尸线程

### 步骤 3：TTS 从 Edge 换回小米原生

```yaml
# xiao_config.yaml
# v1: edge TTS — 音质好但慢（12-30秒生成）
tts: edge

# v2: mi TTS — 小米原生，速度快（1-3秒）
tts: mi
```

| TTS 引擎 | 生成速度 | 音质 | 需要联网 | 适合场景 |
|---------|---------|------|---------|----------|
| edge | 慢（12-30秒） | 好 | 是 | 追求音质的场景 |
| **mi** | 快（1-3秒） | 一般 | 是 | ✅ 语音交互（推荐） |
| azure | 中（5-10秒） | 很好 | 是 | 商业部署 |

### 步骤 4：Hermes 超时降级处理

```python
def _hermes_chat(query: str) -> str:
    cmd = [hermes_bin, "chat", "-q", query, "-Q",
           "--reasoning", "none", "--no-restore-cwd",
           "--max-turns", "10"]
    try:
        result = subprocess.run(
            cmd, capture_output=True, text=True,
            timeout=HERMES_TIMEOUT,  # 60秒超时
            env={**os.environ, "HERMES_QUIET": "1"},
        )
        # 清理 Hermes 输出中的 reasoning 框线字符
        output = _clean_hermes_output(result.stdout)
        return output or "[Hermes returned empty response]"
    except subprocess.TimeoutExpired:
        return "[Hermes 超时，请稍后再试]"  # 降级提示
    except Exception as e:
        return f"[Hermes 调用失败: {e}]"
```

超时后返回友好提示而非让用户干等，同时 `--reasoning none` 跳过推理步骤进一步加速。

## 方案对比

### 优化前后整体对比

| 指标 | v1（优化前） | v2（优化后） | 提升幅度 |
|------|------------|------------|----------|
| 简单聊天响应 | 13-43秒 | 3-5秒 | **~8倍** |
| 系统操作响应 | 16-127秒 | 15-60秒 | **~2倍** |
| 超时率 | 33%（1/3超时） | <5% | **大幅降低** |
| 并发能力 | 1（单线程） | 多线程 | **质的飞跃** |
| TTS 延迟 | 12-30秒 | 1-3秒 | **~10倍** |

### Bridge 路由策略对比

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 全走 Hermes | 功能最强（工具+记忆+技能） | 太慢（11s+冷启动） | 不适合语音交互 |
| 全走 CANNBOT | 快（3.5s） | 无工具调用能力 | 纯聊天场景 |
| **关键词路由** ✅ | 简单聊天快，复杂任务强 | 关键词需调优 | ✅ 混合场景 |
| 意图分类（NLU） | 更精准 | 需要训练模型，复杂 | 高级场景 |

### HTTP Server 方案对比

| 方案 | 并发模型 | 依赖 | 适合场景 |
|------|---------|------|----------|
| HTTPServer | 单线程同步 | 零依赖 | 极低并发 |
| **ThreadingHTTPServer** ✅ | 多线程 | 零依赖 | ✅ 中低并发 |
| ForkingHTTPServer | 多进程 | 零依赖 | CPU 密集 |
| uvicorn + FastAPI | 异步 ASGI | 需安装 | 高并发生产 |

## 避坑提示

- **触发词设计是核心**：不要用 `帮`、`查`、`看` 等高频日常词作为 Hermes 触发词，否则 90% 的对话都走慢路径。应该用 `执行/部署/重启` 等明确的系统操作动词
- **`ThreadingHTTPServer` 要设 `daemon_threads = True`**：否则主进程退出时子线程不会终止，导致端口占用
- **Edge TTS 不适合实时语音交互**：生成速度与文本长度正相关，长回答要等 30 秒。语音交互场景优先用设备原生 TTS
- **Hermes CLI 每次都是冷启动**：不像 Web 服务可以常驻内存，每次 `hermes chat -q` 都是新进程，至少 11 秒。如果需要高频调用，考虑用 `hermes proxy` 模式常驻
- **`--reasoning none` 可以加速 Hermes**：跳过推理步骤直接出结果，适合不需要深度思考的简单查询
- **超时降级比干等好**：60 秒超时后返回"[超时，请稍后再试]"，比让用户等 120 秒什么都听不到强得多
- **`subprocess.run` 的 `capture_output=True` 会缓冲全部输出**：如果 Hermes 输出很长（如代码生成），内存占用会增大。可以用 `Popen` + 逐行读取替代

## 相关知识

### Python HTTP Server 并发模型

Python 标准库 `http.server` 提供了三种 Server 类：

- **`HTTPServer`**（`socketserver.TCPServer` 子类）：单线程同步，一个请求处理完才处理下一个。适合调试，不适合生产
- **`ThreadingHTTPServer`**（`socketserver.ThreadingMixIn` + `HTTPServer`）：每个请求一个线程，互不阻塞。适合 I/O 密集型（如等待 LLM 响应）
- **`ForkingHTTPServer`**（`socketserver.ForkingMixIn` + `HTTPServer`）：每个请求一个进程，隔离性好但开销大。适合 CPU 密集型

对于 Bridge 这种"大部分时间在等 LLM API 响应"的 I/O 密集型场景，`ThreadingHTTPServer` 是最佳选择——零依赖、足够快、不需要异步框架。

### SSE 流式响应原理

Bridge 支持 `stream: true` 模式，使用 Server-Sent Events (SSE) 协议：

```
HTTP 响应头: Content-Type: text/event-stream
数据格式: data: {"choices":[{"delta":{"content":"你好"}}]}

结束标记: data: [DONE]

```

SSE 允许服务端逐步推送数据，客户端边收边显示。但 xiaogpt 的 TTS 是在收到完整文本后才合成的，所以流式响应主要减少的是"首字节延迟"（用户更快看到开始回复），对"完整响应时间"帮助不大。

### TTS 引擎选型考量

语音交互场景下，TTS 延迟是用户体验的生死线：

- **首字节延迟 < 1 秒**：用户感觉"即时回应"
- **1-3 秒**：可接受，类似人类思考停顿
- **> 5 秒**：用户会以为设备故障

小爱原生 TTS（`mi`）在小米云端合成，延迟 1-3 秒；Edge TTS 在微软云端合成，延迟 5-30 秒。对于智能家居场景，**速度 > 音质**，优先选原生 TTS。
